이 두 파일도 확인했습니다 — 결론: **`_1to3_only` 필터의 정의는 여기에도 없습니다.** 하지만 이 파일들이 그 필터의 위치를 최종적으로 좁혀줬고, 코드 없이도 질문을 확정할 수 있는 데이터 확인법이 생겼습니다. 쉽게 정리합니다.

**run9c가 하는 일 — 필터가 아니라 순수 merge입니다.** 셸 스크립트를 보면 네 패널이 전부 **입력**입니다: `panel_event_monthly_matched_final_clean.csv`(main)과 `..._1to3_only.csv`(strict)가 이미 존재해야 하고("panel file not found"면 에러 종료), run9c는 거기에 SonarQube 메트릭을 **왼쪽-조인으로 붙이기만** 합니다. `merge_sonarqube_panel_v2.py`는 깨끗합니다: `validate="one_to_one"` + 행 수 보존 assert(행이 늘거나 줄면 즉시 실패), 결측 미대치·미삭제 정책 명시(docstring "Do not impute / Do not drop"), 원시값은 `*_raw`로 보존. 그리고 중요한 정합성 하나 — `static_analysis_warnings = bugs_raw + vulnerabilities_raw + code_smells_raw`를 일반 `+`로 계산하는데, pandas에서 일반 `+`는 성분 하나라도 NaN이면 결과가 NaN이라 run9e의 `min_count=3`과 **동일한 보수적 동작**입니다. 두 단계의 결측 정책이 일치함을 확인했습니다. 또 main과 strict가 **같은** 메트릭 파일(`jsts_sonarqube_main/...`)을 받으므로, 두 설정의 차이는 오직 패널 멤버십뿐 — 비교 가능성도 확보됐습니다.

**그래서 필터 정의는 run9c의 상류, 즉 `panel_event_monthly_matched_final_clean*.csv` 네 개를 만든 빌더**(아마 run9a/9b 계열 + 그 파이썬)에 있습니다. 체인이 이제 완전히 그려졌습니다: 논문 matching.csv 상속 → run8c(클론 필터, usable_pairs + coverage 생성) → **[미확인: run9a/9b 패널 빌더 — 여기가 main/strict 분기]** → run9c(SonarQube merge) → run9e(quality DiD input) → Rmd.

**그런데 그 파일을 기다리지 않고도 질문을 확정할 방법이 있습니다.** run8c가 만든 coverage 파일(`num_usable_controls` per treatment)과 두 패널을 직접 대조하면, "1개라도 vs 3개 전부 vs 짝 control만" 중 무엇인지 데이터가 답합니다:

```python
import pandas as pd
D = "tmp_jsts_test/data"
m = pd.read_csv(f"{D}/jsts_did_final/panel_event_monthly_matched_final_clean.csv")
s = pd.read_csv(f"{D}/jsts_did_final/panel_event_monthly_matched_final_clean_1to3_only.csv")
pairs = pd.read_csv(f"{D}/jsts_matched_control_pairs_main_398_clone_usable.csv")
cov = pd.read_csv(f"{D}/jsts_control_pair_coverage_main_398_clone_usable.csv")

mt = set(m.loc[m.ever_treated==1,"repo_name"]); st = set(s.loc[s.ever_treated==1,"repo_name"])
mc = set(m.loc[m.ever_treated==0,"repo_name"]); sc = set(s.loc[s.ever_treated==0,"repo_name"])
print("treated  main/strict/strict에서빠짐:", len(mt), len(st), len(mt-st))
print("control  main/strict/strict에서빠짐:", len(mc), len(sc), len(mc-sc))

# 가설 A: strict treated = usable control 3개 전부 보유한 treated
covA = set(cov.loc[cov.num_usable_controls==3,"treatment_repo"])
# 가설 B: strict treated = usable control 1개 이상 보유한 treated
covB = set(cov.loc[cov.num_usable_controls>=1,"treatment_repo"])
print("가설A(3개 전부 요구)와 일치?", st == (covA & mt))
print("가설B(1개 이상)와 일치?",   st == (covB & mt))

# control 쪽: strict control이 '유지된 treated의 짝 control'로 정확히 한정되는지
paired = set(pairs.loc[pairs["treatment_repo"].isin(st), "control_repo"])
print("strict control ⊆ 유지 treated의 짝 control?", sc <= paired)
print("strict control == 그 짝 control 전부?", sc == (paired & mc))
```

읽는 법: 가설A가 True면 "3개 전부 usable인 treated만 유지"(가장 엄격), 가설B가 True면 "1개라도 있으면 유지", 마지막 두 줄이 True면 "control은 유지된 treated의 짝만 남김"이 확정됩니다. main 375 vs strict 333(−42)이라는 차이 규모로 보면 가설A(3개 전부 요구)일 가능성이 높지만, 이 스니펫이 추측을 확정으로 바꿔 줍니다.

판정에 주는 의미는 변하지 않습니다 — 어느 가설이든 strict는 논문에 없는 **추가 제약**이고, 논문 설계(control pool, treated는 coverage 무관 유지)와 동형인 것은 main입니다. 이 스니펫은 strict를 robustness로 보고할 때 "정확히 무슨 제약인지" 한 줄로 쓰기 위한 마지막 확인입니다. 스니펫 결과(또는 run9a/9b 빌더 파일) 주시면 이 건은 종결하고, 보고서 문구까지 정리해 드리겠습니다.
